# Agent API v1

Status: accepted under [ADR-0020](../decisions/0020-agent-api-and-request-provisioning.md).
Implemented locally: registration/token management, signed `/me`, access-request
create/list/get/cancel, and operator list/detail/reject/cancel. Approval, resume,
issuance, and the agent-authenticated protected-query facade remain planned.

Date: 2026-09-25

## Boundary And Ownership

The public SDK connects to the `demo-console` origin. Explicit route handlers expose
agent operations. Operator routes retain cookie-session authentication and CSRF
checks. There is no generic backend proxy and no agent-cookie fallback.

`demo-gateway` and owner RPCs remain private. The console's agent handlers use a
trusted server-side caller context, never a caller-supplied agent ID, for owner RPCs.
Internal services accept calls only from the configured owner facade network identity.
Agent containers have no access to internal datasets, registries, queues, or volumes.

The console owns token administration, authenticated HTTP routing, and operator views.
New owner-only access-request RPCs in `services/razield` own request transitions and
private intent storage. A separate role in that service runs the BullMQ dispatcher.
The existing administrative tool boundary owns policy approval and networked SpiceDB
provisioning. The gateway retains data access and independent verification. New RPC
messages are separate from the frozen verifier request descriptor.

Deployment configuration supplies an audience equal to the installation trust domain.
It is independent of hostnames, ports, tunnels, and reverse proxies. A different
installation uses a different audience. Use HTTPS for nonlocal public access. Local
loopback or an SSH tunnel can carry HTTP for development. Do not weaken operator
origin checks to accommodate server-to-server agent calls.

## Agent Registration

The authenticated operator creates a registration with a display name and a raw
32-byte Ed25519 public key. Rust validates its encoding and rejects weak keys before
storage. The server allocates `agentId`, derives the ADR-0014 thumbprint, and enforces
one registration per key within the installation. Display names confer no authority.

Registered keys are immutable. Changing a key creates a new registration and requires
new capabilities. Token rotation keeps the registration and key. Revoked or expired
tokens cannot read even their own request records.

The operator creates a token with a required expiry, at most 90 days from creation.
The UI defaults to 30 days. The secret is displayed once in the create response:

```text
rz1.<tokenId>.<secret>
tokenId = 16 cryptographically random bytes, lowercase hex (32 characters)
secret = 32 cryptographically random bytes, unpadded base64url (43 characters)
```

Persist token ID, agent ID, audience, SHA-256 of the complete ASCII token, creation,
expiry, and optional revocation time. Compare fixed-length digests in constant time.
The high-entropy secret is generated by the server, not supplied as a password.
Never store or log the plaintext token. A lost create response requires a new token
and revocation of the unknown one. List responses show metadata only.

## API Authentication

Every agent request supplies these single-valued headers:

| Header | Exact representation |
| --- | --- |
| `Authorization` | `Bearer ` followed by the canonical token |
| `X-Raziel-Agent-Version` | `1` |
| `X-Raziel-Agent-Timestamp` | Nonnegative whole Unix seconds as canonical decimal |
| `X-Raziel-Agent-Nonce` | 32 random bytes as 64 lowercase hex characters |
| `X-Raziel-Agent-Signature` | 64 Ed25519 signature bytes as 128 lowercase hex characters |

No public-key header chooses a different identity. The verifying key comes from the
token's registration. Reject duplicate, comma-joined, oversized, or malformed auth
headers. Never put credentials in URLs. Hash the exact received HTTP body before
parsing it. Empty GET bodies hash as zero bytes. Reject content encodings and GET
bodies so intermediaries cannot silently transform the signed bytes.

The signature covers `framed_message("raziel/agent-api-request/v1", payload)` directly.
Framing is `u32be(domain_length) || domain || u32be(payload_length) || payload`.
The ordered payload is:

```text
u32be(1)
string(audience)
string(tokenId)
bytes(agentKeyThumbprint)       # 32 bytes, ADR-0014
string(requestMethod)
string(canonicalRequestTarget)
bytes(SHA256(exactHttpBody))    # 32 bytes
bytes(requestNonce)            # 32 bytes
i64be(requestTimestamp)        # two's-complement UTC seconds
```

`string` is `u32be(byte_length)` plus exact UTF-8 bytes. `bytes` has the same length
prefix. No Unicode normalization occurs. Audience is printable ASCII, 1-128 bytes.
Token ID is exactly 32 lowercase hex characters. Timestamp is within Protobuf's
nonnegative whole-second range, up to `253402300799`. Fields are validated before
encoding. No JSON or Protobuf serialization becomes a cryptographic commitment.
The HTTP body hash authenticates transport bytes, not authorization semantics.

Reuse [ADR-0002](../decisions/0002-protected-request-signature-envelope.md) method and
target rules. The facade reconstructs the method and origin-form target from the
actual route. It ignores caller-supplied canonical-target headers. The SDK sends the
canonical path it signed, without redirects. Path-changing proxies need explicit
configuration and a deployment test, not trust in arbitrary forwarded headers.

Accept timestamps from `now - 300` through `now + 30`, inclusive. Require token
validity at both timestamp and current time. Strict Rust Ed25519 verification must
pass before replay storage. Atomically consume `(audience, tokenId, nonce)` until
`timestamp + 301`. A failed downstream call does not release the nonce. Redis failure
fails closed. Retries sign a fresh transport nonce but retain operation identity.

Registration status, token status, and nonce consumption share an atomic Redis check
after signature validation. Token revocation wins against any later check. An operation
admitted before revocation can finish. No positive token-status cache is allowed.

The Rust helper accepts one bounded local request, validates key/envelope bytes, and
returns a thumbprint or a coarse rejection. It does not accept tokens or private keys.
Limit input to 8 KiB, output to 1 KiB, and execution to two seconds. A helper failure
returns service unavailable, never an authenticated caller.

## HTTP Surface

New workflow messages will live in `proto/raziel/v1/agent_api.proto`. Buf generates
the DTOs. HTTP uses their strict ProtoJSON mapping, lower-camel fields, decimal strings
for 64-bit integers, canonical padded base64 for `bytes`, and no unknown fields.
All versioned messages require `formatVersion: 1`. Reject unknown enum values.
HTTP authentication uses the separate header encoding above.

| Method and path | Input | Result |
| --- | --- | --- |
| `GET /api/agent/v1/me` | No body | Own ID, public key, thumbprint, audience, token expiry, API version |
| `POST /api/agent/v1/access-requests` | `AccessIntent` | 201 for new request, 200 for exact retry |
| `GET /api/agent/v1/access-requests` | Optional cursor, limit 1-50 | Own request projections only |
| `GET /api/agent/v1/access-requests/{requestId}` | No body | Own `AccessRequest` |
| `POST /api/agent/v1/access-requests/{requestId}/resume` | Expected generation | Rejoin dispatch after offline-agent reservation expiry |
| `POST /api/agent/v1/access-requests/{requestId}/issuance` | Proposal ID, generation, signed `CreateCapabilityRequest` | 202, retained attempt and public request state |
| `POST /api/agent/v1/access-requests/{requestId}/cancel` | Expected generation | 202 cancellation accepted, or 200 retained terminal result |
| `POST /api/datasets/{datasetId}/protected-query` | Existing M5 protected-query envelope | Existing bounded rows, receipt, and verifier/cache indicator |

The last route is an explicit agent-authenticated facade at the same path as the
internal gateway. It forwards the exact bounded envelope only to that protected
route. It does not expose `/query`, dataset administration, or internal service URLs.
Both the API signature key and the ADR-0002 protected-request key must match the
registration. The inner signature retains the existing query-byte hash and gateway
target rules. The outer signature covers the full transported envelope. Neither
signature replaces the other. There is no target-rewriting shortcut.

Operator endpoints live under `/api/operator/agents` and `/api/operator/access-requests`.
They support register/list, create/list/revoke tokens, review/approve/reject, and cancel.
An approval includes the expected request generation, exact policy record ID, dataset
revision, and a bounded owner-only grant recipe. New policy publication uses the
existing policy-authority boundary with the migration below. Agent credentials never
grant access to those operations.

## DTO Fields And Privacy

`AccessIntent` fields:

- `requestId`: caller-generated UUIDv4, persisted before the first send.
- `taskId`, `purpose`, `action`: existing bounded claim strings. Initial action is `query`.
- `datasetId`, `datasetRevision`: exact finalized resource selection, not a mutable latest alias.
- `requestContext`: at most 16 existing typed context entries, at most 16 KiB total input.
  The values are caller inputs, not authoritative stored caveat values.

The server assigns owner identity, creation time, a 24-hour review/dispatch deadline,
and generation 1. The same registration and request ID return the retained request
only for equal normalized typed intent fields. Different fields yield `CONFLICT`.
The durable identity is `(agentId, requestId)`, not the UUID alone. Storage references,
queue IDs, cancellation, and recovery use that owner-qualified identity. Two agents
choosing the same UUID remain separate. The URL's request ID is always resolved under
the authenticated registration.
No client-provided agent ID, policy hash, or display label overrides server identity.
Context is compared inside private storage, never exposed through an equality digest
or a context echo in public lists. Unknown datasets yield a coarse non-disclosing error.

`AccessRequest` fields are request ID, owner ID, task/purpose/action, dataset ID and
revision, state, monotonically increasing generation, created/updated/deadline times,
optional public policy binding, optional proposal, proof job ID/state, metrics,
capability, and coarse error code. Omit absent alternatives. No relationship, recipe,
stored context, schema, PolicyIR, or private diagnostic reference is returned.

An `IssuanceProposal` contains opaque proposal ID, generation, signature deadline,
registered public key, task/purpose/action, exact resource type/scope, policy record ID
and hash, snapshot ID/root, and requested expiry. It contains no request context.
The SDK uses the original intent's context from its own storage. It validates the
proposal against the intent and configured key before signing. A generation mismatch
or changed scope requires a refreshed approval, not silent signer acceptance.

The agent generates the issuance nonce and signs the existing ADR-0011 commitment.
It persists the full signed request before `/issuance`. The server compares every
bound field and private context against the proposal and original intent. Policy
record/hash are resolved through the proposal's signed snapshot, not caller metadata.
The commitment-derived job ID remains ADR-0014's exact identity.

`capability` returns the bounded serialized `ProofCapability` as Protobuf `bytes`
with a separate safe claims projection. The SDK decodes through generated messages.
It builds the existing M5 hex transport internally for protected queries. This is a
new API transport choice, not a new proof artifact or global M5 transport migration.
The verifier still performs its existing strict Protobuf check.

Bound workflow bodies to 16 KiB, public capability responses to 2 MiB decoded artifact
size, and protected envelopes to the current 6 MiB ceiling. Lists contain at most 50
safe summaries and never embed proof bytes. Cursors are opaque and owner-scoped.

## Lifecycle And Dispatch

### Operator Approval Input

The operator-only `POST /api/operator/access-requests/{agentId}/{requestId}/approve`
accepts `formatVersion: 1`, `expectedGeneration`, `policyRecordId`, `policyVersionId`,
`approvalEpoch`, and `grant`. Generation and epoch use canonical positive decimal
strings. `grant` contains `formatVersion: 1`, `teamId`, `organizationId`,
`approvedAmount` (positive decimal string within JavaScript's safe integer range),
and Boolean `isApproved`, `isSuspended`, and `isOverride` fields. These inputs cover
the existing visual rule families. They stay in the owner's private approval file.

The facade checks the operator session and CSRF token, then reads finalized dataset
metadata itself. The owner compares that metadata to the private original intent,
resolves the exact installed current policy approval, and retains an immutable
dataset binding. Callers cannot supply a checksum, resource alias, PolicyIR, or
agent key override. Successful approval enters `APPROVED_WAITING`, not a proof job.

An exact retained approval retry can omit the dataset lookup inside the owner RPC.
That lookup-only operation cannot create an approval. New approval requires current
trusted dataset metadata. Changed selection or private grant inputs conflict with
the retained approval. Cancellation or expiry never returns to an approved state.
The original agent identity, task, purpose, action, and context remain bound through
the existing private intent. Dispatch must recheck policy validity before preparation.

| State | Entered by | Permitted next states |
| --- | --- | --- |
| `PENDING_REVIEW` | New authenticated intent | `APPROVED_WAITING`, `REJECTED`, `CANCELED`, `EXPIRED` |
| `APPROVED_WAITING` | Operator approval or explicit resume | `PREPARING`, `CANCELED`, `EXPIRED`, `FAILED` |
| `PREPARING` | Dispatcher with free proof capacity | `AWAITING_SIGNATURE`, `CANCELLING`, `EXPIRED`, `FAILED` |
| `AWAITING_SIGNATURE` | Durable policy/snapshot proposal | `SUBMITTING`, `WAITING_FOR_AGENT`, `CANCELED`, `EXPIRED`, `FAILED` |
| `WAITING_FOR_AGENT` | Signature reservation elapsed | `APPROVED_WAITING`, `CANCELED`, `EXPIRED` |
| `SUBMITTING` | One persisted valid signed attempt | `QUEUED`, `EXECUTING`, `PROVING`, `READY`, `CANCELLING`, `FAILED` |
| `QUEUED`, `EXECUTING`, `PROVING` | Authoritative existing proof job | Later proof phase, `READY`, `CANCELLING`, `FAILED`, `CANCELED` |
| `CANCELLING` | Durable cancel command | `CANCELED`, `READY`, `FAILED` after reconciliation |
| `READY`, `REJECTED`, `CANCELED`, `EXPIRED`, `FAILED` | Confirmed terminal result | None |

`READY` means a completed capability, not perpetual authorization. Its independent
expiry still governs queries. A cancellation racing with completed proof success can
return `READY`. Cancellation acceptance never claims confirmed termination.

Use one Rust access-dispatch worker, backed by the existing BullMQ/Redis dependency,
with global and local concurrency one. Jobs carry agent ID, request ID, and generation only,
within the existing 256-byte queue payload budget. A durable request record and private
intent envelope are stored before enqueue. A restart reconciler repairs a missing
dispatch reference idempotently. Redis CAS guards state and generation, not a custom
replacement job queue.

The dispatcher holds its workflow slot through snapshot preparation, a maximum
120-second signing wait, and an admitted proof's terminal result. Its BullMQ lock is
renewed by the library. Policy publication uses a different short writer operation.
Only the existing proof worker executes SP1. Its one attempt and zero stalled retries
stay unchanged. Dispatcher recovery reconciles an existing attempt, never retries a
failed proof. Missing or unreadable proof state is not success or cancellation.

After signature timeout, invalidate the proposal generation, release dispatch capacity,
and require explicit authenticated `/resume`. The SDK can resume once after reconnect.
Do not spin an offline agent through repeated snapshot creation. A late signature
cannot start the expired proposal. Prepare a fresh proposal after resume.

After snapshot publication, choose proposal time `T`, requested expiry `T + 4800`,
and signing deadline `T + 120`, all UTC seconds. Require policy, snapshot, delegation,
and relevant authority bounds to cover that requested expiry. At worker start `W`,
existing admission requires `W + 4500 <= T + 4800`. The resulting capability remains
bounded by `W + 4500`. A missed admission window fails the attempt. It never silently
changes signed timestamps. A new attempt needs a new explicit access request.

Check current registration and token status on signature submission. Token revocation
blocks further external calls, but does not cancel a running proof automatically.
Operator cancellation is explicit. Proof-bound validity remains separate from token
expiry. A rotated same-key token can recover that registration's pending request.

Persist one signed attempt and deterministic job ID before any create RPC. Reconcile
`GetCapability` first after a timeout. Confirmed absent state can resend only the same
signed bytes and only without pending cancellation. Preserve ambiguity and report
`SERVICE_UNAVAILABLE` rather than mint a new nonce. Pin the accepted proposal generation
through cancellation and recovery.

Persist a cancellation flag before attempting a proof cancel RPC. It blocks every
later submission or recovery resend. An already outstanding create can still publish,
so a missing job at one instant cannot confirm cancellation. Reconcile the outstanding
attempt, cancel a discovered job through the existing durable cancellation boundary,
and confirm its terminal state and cleanup before releasing capacity. Unresolved
publication stays `CANCELLING` and unavailable, never presumed absent. No automatic
second proof is permitted. Repeated cancel calls return the retained command/result
before rejecting an otherwise stale generation.

Start with 100 nonterminal requests per installation and 16 per agent. Reject excess
admission without private side effects. Terminal request records and idempotency data
remain for seven days. Copy public proof results into request storage before releasing
the workflow slot, independently of the proof queue's 24-hour/100-record retention.
Remove private issuance/proving envelopes after confirmed terminal cleanup. Retain the
minimal normalized private intent comparison record, including its supplied context,
in owner-only storage for the same seven-day idempotency window. It is not a witness
or a queue payload. Delete it with the request record at retention expiry. Public
responses and logs never expose it.
Snapshots retain the existing owner-only lifecycle. Expired request IDs cannot be
retried transparently after retention. The SDK requires explicit new user intent.

## Errors And Retry Rules

Errors use `{ error: { code, retryable } }`, with no stack or policy explanation.

| HTTP | Code | Client behavior |
| --- | --- | --- |
| 400 | `INVALID_REQUEST` | Correct shape, version, or bounds |
| 401 | `NOT_AUTHORIZED` | Check token/key/clock, no blind retry |
| 403 | `NOT_AUTHORIZED` | Protected scope or verification failed, no rows |
| 404 | `NOT_FOUND` | Unknown or not owned, identical response |
| 409 | `CONFLICT` | Refresh generation or preserve original idempotent input |
| 409 | `REQUEST_REPLAYED` | Fresh transport signature, same operation ID |
| 410 | `EXPIRED` | Explicit new request, no automatic reproving |
| 429 | `CAPACITY_EXCEEDED` | Honor bounded Retry-After, no new request ID |
| 503 | `SERVICE_UNAVAILABLE` | Reconcile status, bounded retry with fresh auth nonce |

Use the existing protected-query coarse error contract inside the facade. A response
timeout is an unknown outcome. SDK polling defaults to five seconds, backs off to 30,
honors Retry-After, and accepts an AbortSignal and caller deadline. Aborting a local
wait does not cancel a server job. State reads never trigger proof execution.

Protected queries have two replay envelopes. A retried read uses a fresh inner
ADR-0002 nonce, timestamp, and signature, then a fresh outer API signature over the
new serialized envelope. It reuses the same capability and query scope. It can create
another read receipt after an uncertain response, not another proof. Do not apply
this read-only retry behavior to a future side-effecting dataset operation.

## Policy Package Migration

Implementation checkpoint: the owner-only `/api/policies/versions` preparation/read
routes allocate immutable identities and compile private namespaced candidates.
Preparation does not approve policies or provision snapshots. The separate
`POST /api/policies/versions/{candidateId}/publish` route calls an explicitly
configured composed owner role. It approves and retains the exact package, checks
live schema drift, and installs the aggregate with durable uncertain-write recovery.
Two coexisting versions and exact retries passed against pinned SpiceDB locally.
The opt-in M6 runtime connects the visual builder to this role and removes legacy
writers from its service set. Its two-version browser publication passed locally.
M5 remains the default. The legacy activation adapter rejects the reserved namespace,
and both writers must not run against the same schema.
The [inbox runbook](../runbooks/AGENT-ACCESS-INBOX.md#policy-version-preparation)
records the current operator contract.

New families use opaque 32-lowercase-hex IDs. Versions have separate IDs of the same
form and positive integer version numbers. Allocate numbers atomically. Signed names
use `family:<familyId>:v<version>` within the existing 128-byte policy-name bound.
No display-name alias participates in policy resolution.

Generate identifiers from the version ID: `dataset_<id>`, `team_<id>`,
`organization_<id>`, and `caveat_<id>_<index>`. All names remain within 63 characters.
Keep only the shared empty `agent` definition outside that namespace. Typed draft
rendering produces both the isolated source package and its definition inventory.
Do not rewrite source strings with a search-and-replace pass.

Each retained package records its source bytes/digest, canonical PolicyIR/hash, exact
signed approval record, generated name inventory, compiler configuration/pins, and
private owner mapping. The existing signature covers its existing approval claims,
not a newly invented signature over the whole package.
It references the existing source manifest rather than changing guest fields.
Approved packages survive candidate cleanup. The public browser sees draft controls
and safe status, never the retained package or grant file.

One networked SpiceDB provisioner composes all installed packages, shared `agent`
once, plus a validated legacy M5 package. It is separate from the networkless registry
writer. Compile and compare definition/caveat inventories before writing.
Reject duplicate ownership, changed definitions, cross-version references, unexpected
live schema drift, or unsupported constructs. No implicit schema deletion is allowed.
The package digest remains the digest of its own exact source, not the composition.
The snapshot authority checks that its selected package is in the accepted composition
at the exact read revision. This retains the existing trusted snapshot-provenance model.

Persist the aggregate generation, exact schema digest, and constituent package IDs
separately from policy commitments. Verify each source digest, canonical PolicyIR hash,
signed approval, type inventory, and reference ownership before installation. An
expired or revoked package remains installed but cannot authorize new snapshots.
Reapproval is explicit supersession of that version's prior record, not transparent
renewal for existing proofs. Do not reuse one policy hash under different signed names.

Legacy import requires the original exact source bytes and compiler configuration
matching the historical source digest. A reflected equivalent schema is not those
bytes. Missing legacy source blocks new legacy snapshots, not verification of retained
proofs. Seed explicit legacy dataset bindings instead of allowing every `dataset` type.

Start with at most 32 installed new version packages, 1 MiB of composed UTF-8 schema,
and 1 MiB of compiled schema reflection, retaining the existing 2 MiB transport ceiling.
Check aggregate size before activation and installation. Do not widen the 16-definition
per-policy, 256-relationship per-snapshot, or 4 KiB private-input guest limits. Exercise
the supported namespaced rule families against those limits before shipping them.
Grant retirement is explicit owner maintenance, never truncation during snapshotting.

Provisioning state is keyed by request and proposal generation, not candidate ID.
Persist grant-write and revision handoff state privately. Retries reuse an exact
completed handoff or reconcile an uncertain write before creating another snapshot.
Read only types in the selected PolicyIR at that revision. Current snapshot tuple and
guest limits still apply. Exceeding them fails the request rather than dropping tuples.
An older proof reads its stored snapshot even after later relationship writes.

Registry mutation remains generation-checked. A concurrent policy publication can
advance the generation after a successful root append. Confirmation must compare the
exact descriptor and accepted root in a validated generation at least as new as the
append result. A newer unrelated generation alone is not failure. A conflicting root,
revoked bound record, or missing descriptor still fails. Retry generation conflicts
without replacing the original committed snapshot or extending the short writer lock
through agent signing or proving.

Store an immutable trusted binding `(policy_hash, resource_type, resource_scope)` to
dataset ID, finalized revision/checksum, and allowed action. The signed request includes
that resource type/scope. Dispatch and both cold and cached gateway paths check the
binding and the dataset in the signed target. Unknown mappings, changed revisions,
retargeted aliases, or type-prefix matches alone release no data. No guest change is needed.

The owner stores version-1 binding JSON under
`<root>/<policy_hash>/<resource_type>/<resource_scope>.json`. Its exact fields are
`format_version`, `policy_hash`, `resource_type`, `resource_scope`, `dataset_id`,
`dataset_revision`, `dataset_checksum`, and `action`. Revision is a canonical positive
decimal string within JavaScript's safe integer range. Hashes are lowercase SHA-256
hex. Directories are `0700`, files are `0600`, and records are bounded to 4 KiB.
No overwrite or alias retargeting is allowed. This is trusted owner routing metadata,
not a new commitment input or standalone authorization grant.

`RAZIEL_DATASET_BINDING_MODE=required` selects exact mapping in the M6 gateway.
`RAZIEL_DATASET_BINDING_ROOT` is a read-only owner volume. Missing configuration and
invalid records fail closed. The separate default M5 runtime remains in `legacy`
mode until explicit migration. The M6 approval writer is connected. Dispatch and
the external agent protected-query integration remain B-0066 work.

## SDK And Implementation Order

```ts

// me, createAccessRequest, listAccessRequests, getAccessRequest,
```

Copy and derive identity from the signer's raw public key. Reject malformed signature
lengths. Never accept a supplied thumbprint as authority. The SDK does not own key
storage or silently generate a replacement identity. The demo agent persists its key,
intent, proposal, and signed attempt in its private volume before outbound operations.

Move SDK ownership once into the sibling public package. Ship ESM, declarations,
public generated DTOs, README, license, and compatibility metadata. Exclude private
workspace dependencies, server registry types, credentials, fixtures, and witness
modules. Pin backend protocol revision and canonical vectors in release metadata.
Build a tarball for local cross-repo tests, then publish the reviewed public release.
Backend consumers migrate to that package rather than maintaining two implementations.

protobuf runtime `2.12.1`, Vitest `4.1.10`, Biome `2.5.4`, Node types `24.13.3`.
